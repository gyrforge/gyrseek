## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- When the user types `/graphify`, invoke the `skill` tool with `skill: "graphify"` before doing anything else.
- Always rerun `/graphify` via `graphify update .` after every code change to keep graph artifacts current before handing off or committing (AST-only, no API cost).

## Mandatory Pre-Session Setup

All skills below only apply to code changes within this branch/session,
not the entire codebase.

1. **Load ponytail** — Enforces the lazy engineering ladder: does it need to
   exist? Does stdlib cover it? Can it be one line? The shortest path to done
   is the right path. Default intensity: full. Override with `/ponytail lite|ultra`
   or `stop ponytail` for normal mode.
   **Note:** Rust idioms take precedence over ponytail recommendations when
   they conflict. The shortest path is idiomatic Rust, not necessarily the
   fewest lines.
2. **Load interrogation** — Available on demand via `/grill`, `/interrogate`,
   "grill me", "stress-test this plan", or "pick this apart". See
   `.agents/skills/interrogation/SKILL.md` for full details.
3. **Load code-security** — Active for all code writing and review. Automatically
   checks for vulnerabilities relevant to the language and patterns in use.
   See `.agents/skills/code-security/SKILL.md` for full details.

## Agent Portability Symlinks
- `.claude/skills` → `.agents/skills` (folder-level symlink; auto-picks up new skills)

- `CLAUDE.md` → `AGENTS.md` (changes to AGENTS.md propagate instantly to Claude Code)
- `.github/CODEOWNERS` must name the **real** files, not the symlinks: a pull request that edits `.agents/skills/x` changes that path, never `.github/skills/x`, so a rule on the link protects nothing. It lists `.agents/`, `.claude/` (`settings.json` holds shell hooks), `.opencode/` (a JavaScript plugin), `AGENTS.md`/`CLAUDE.md`, `.github/copilot-instructions.md`, `.coderabbit.yaml`, `skills-lock.json`, `.githooks/` (the pre-commit hook runs on every commit of anyone who sets `core.hooksPath`), `.gitattributes` (can hide a diff in review), the workflow and everything CI executes (`justfile`, `tests/`, `docker/`, `Cargo.toml`, `Cargo.lock`), and the symlinks themselves without a trailing slash. A new file or directory that runs code or steers an agent belongs in it. The owner is the team `@gyrforge/gyrseek-builders`, not individual handles: any member can approve, and a misspelt or departed handle cannot make every review impossible (an earlier `@david-craggs` was not a GitHub account, so GitHub reported a CODEOWNERS error on every line and requested no reviewer). The team needs Write access to the repository (Settings > Collaborators and teams), or GitHub ignores it; check `gh api repos/gyrforge/gyrseek/codeowners/errors` after any change. The `main` ruleset also requires approval of the most recent push by someone other than the pusher, so a pull request needs a member who is not its author. It is enforced only while the `main` ruleset requires code-owner review (a repository setting, not in the repo).

- CI:
  - `.github/workflows/ci.yml` — Runs untrusted PR code with workflow-level `contents: read` permissions (with a scoped job-level `checks: write` exception granted strictly to the `cargo-audit` job). Includes `rust-checks` (lint, test), security audits (`cargo-audit`), and containerized test matrices (`linux-docker-uv-test`, etc.). Automated code reviews are handled via CodeRabbit (`.coderabbit.yaml`). Hardened with zizmor 1.33 in mind (`zizmor --offline --persona auditor .github/workflows/ci.yml` reports nothing): every checkout sets `persist-credentials: false`, every job has a `timeout-minutes` (rust-checks 20, the Docker jobs 30, cargo-audit 15; the slowest job takes under 7 minutes), a workflow-level `concurrency` group cancels a pull request's superseded runs (never pushes to main), Rust comes from `rustup` at the version in the workflow's `RUST_VERSION` (1.100.0, bumped on purpose in its own change; the `dtolnay/rust-toolchain` action is gone), and `checks: write` has its reason next to it. All remaining `uses:` are pinned to full commit SHAs.
  - `.github/workflows/release.yml` — builds and publishes the Linux binaries that `gyrseek-action` downloads. Triggers: a tag `vX.Y.Z` (publishes) and a pull request that edits the file (builds and smoke-tests, publishes nothing). `permissions: {}` at the top; the `verify` job (contents/actions read) refuses a tag whose version differs from `Cargo.toml`, whose commit is not on `main`, whose commit has no successful `ci.yml` run, or that already has a release (releases are never replaced: bump the version); the `build` job (contents read) builds `x86_64-unknown-linux-gnu` on `ubuntu-22.04` and `aarch64-unknown-linux-gnu` on `ubuntu-22.04-arm` with `cargo build --release --locked` at `RUST_VERSION` (must equal the one in `ci.yml`, checked), strips, packs a reproducible `gyrseek-vX.Y.Z-<target>.tar.gz` (sorted names, no owner or timestamps, `gzip -n`) with `LICENSE` and `README.md`, and runs the packed binary (`--version` must print `gyrseek X.Y.Z`); the `release` job is the only one with write permissions, has no checkout, and runs in the `release` environment (create it in Settings > Environments, require a reviewer, limit deployments to `v*` tags): it stops on a leftover draft, writes `SHA256SUMS`, attests build provenance with `actions/attest` (`gh attestation verify <file> --repo gyrforge/gyrseek`), creates the release as a draft with every file and publishes it last (`gh release create --verify-tag --draft`, then `gh release edit --draft=false`), so a failed upload never leaves a public release without files. `.github/dependabot.yml` keeps the SHA pins of the actions current (weekly, one grouped pull request, a 7-day cooldown on new releases). The binary links glibc and OpenSSL 3 dynamically (`reqwest` uses `native-tls`), so it needs Ubuntu 22.04 or newer. Releases and tags: `v1.4.0` was tagged and released before this workflow existed, without files, so the first release with files is the next version (a tag for a version that has a release is refused). Still needed in repository settings: the `release` environment with a reviewer, a ruleset that restricts creating and forbids moving or deleting `v*` tags, and GitHub immutable releases.

- Current behavior highlights:
  - Supports uv add, uv pip install, uv pip sync, uv sync, uv lock (bare and update flags), pip/pip3 install, poetry add/update/install/lock, npm install/i/update, pnpm add/install/i/update
  - Non-registry npm/pnpm CLI specifications (`file:`, `git+`, `https://`, `link:`, `./`, `../`, etc.): when all positional CLI targets are non-registry specs, gyrseek forwards the command directly without triggering the `package.json` fallback (FIXED_FINDINGS.md #11) or failing closed with exit code 1 when no `package.json` exists (FIXED_FINDINGS.md #12).
  - Container process limit: `GYRSEEK_MAX_PROCESSES` (default 256, `GYRSEEK_PIDS_LIMIT` accepted as a fallback), passed as `--pids-limit`. `GYRSEEK_DOCKER_SECCOMP_PROFILE` is deprecated and ignored with a warning; use `--danger-disable-seccomp`
  - Container memory and `/work` tmpfs limit: configurable via `GYRSEEK_MEM_LIMIT` (default `2g`), preventing OOM-kills during heavy native dependency compilation in npm/pnpm/python builds (was FIXED_FINDINGS.md #21).
  - `--version`/`-V` is handled as a leading top-level flag before config load or sandbox init: prints `gyrseek <CARGO_PKG_VERSION>` and exits 0 (works with no config file / no Docker). Only the first arg is matched, so a forwarded command's own `--version` (e.g. `gyrseek pip install foo --version`) is passed through, not intercepted
  - Behavioral anomaly detection compares observed network endpoints across versions
  - Behavioral anomaly detection also compares install-time git clone command signatures across versions and fails closed when new clone behavior appears
  - Behavioral anomaly detection traces `open`, `openat`, and related system calls via `strace` to monitor for attempts to read highly sensitive credential or configuration files (e.g., `~/.aws/credentials`, `~/.npmrc`, `.env`). Syscall return codes are verified (`ret_val >= 0`) so failed accesses never populate baseline traces (closing the baseline poisoning gap, was FIXED_FINDINGS.md #60). If a package accesses sensitive files that older versions did not touch, the install is immediately flagged.
  - If any of the 5 behavioral anomaly checks (network, git clone, process exec, sensitive file read, or suspicious artifact) are triggered, the install is blocked. **Importantly**, the scan does not short-circuit on the first failure. All anomaly checks run to completion and aggregate their failure reasons, ensuring comprehensive reporting on exactly what the malicious package attempted to do.
  - Behavioral anomaly detection also compares install-time process execution signatures across versions and fails closed when a version newly executes a program, or executes it with new/additional arguments (catches the Shai-Hulud "Hades/miasma" class: download Bun and run an obfuscated stealer via `bun run`). Both `execve` and `execveat` syscalls are traced and parsed (`parse_execve_argvs`), preventing `execveat`-based evasion (was FIXED_FINDINGS.md #33). Signatures are `exe|arg1|arg2|...` so both "didn't run bun before, now does" and "ran bun before, now runs bun plus extra" are detected. Sandbox-internal commands (the install probe itself, interpreter discovery) are excluded via `is_harness_command` to prevent version-string false positives. See extract_process_exec_signatures in src/scanning.rs (inline tests: flags_newly_introduced_bun_execution, flags_existing_bun_with_additional_invocation, etc.)

## Mandatory Post-Change Policy
After every code or behavior change in this repository:
1. Update this file (AGENTS.md) with the new behavior, scope, or constraints.
2. Confirm the code is efficient and fast (no unnecessary work, no wasted I/O, caching where beneficial) and idiomatic — prefer iterator adaptors (`.filter_map()`, `.partition()`, `.map().collect()`) over explicit `Vec::new()` + push loops.
3. Run `ponytail review` on the changes and address any over-engineering findings.
4. Run tests and confirm they pass.
5. Rerun `/graphify` with `graphify update .` so `graphify-out/` stays in sync with the latest code.
6. Ensure these updates happen in the same change set whenever possible.
7. If architecture, workflow, or future plan changes, update docs/ARCHITECTURE.md (which also holds the development workflow), docs/ROADMAP.md, and docs/DOCKER_SECURITY.md.
8. If a new finding is identified, add it to `docs/OPEN_FINDINGS.md` and its detailed rationale to `docs/OPEN_FINDINGS_DETAILED.md`. When a finding is fixed, move it to `docs/FIXED_FINDINGS.md` and `docs/FIXED_FINDINGS_DETAILED.md`. If it is excluded from fixing, move it to the `WONT_FIX` equivalents. Summary tables live only in the main files (`FIXED_FINDINGS.md`, `WONT_FIX_FINDINGS.md`, `OPEN_FINDINGS.md`); the `_DETAILED.md` files contain only prose entries. All finding IDs use a single flat numeric namespace (no category prefixes). When adding new findings, choose the next available number across all three categories to avoid collisions. **Omit line numbers from finding entries** — they drift as code evolves and are not a contract; use the file name only (e.g. `src/lib.rs`, not `src/lib.rs:210`).
9. **Refresh the pinned sandbox image digests when due.** The Python and Node sandbox images are pinned by digest of a mutable tag (`PYTHON_IMAGES` and `NODE_IMAGES` in `src/runtime_image.rs`), so the pins go stale as base images get security updates. Do this whenever the change touches `src/runtime_image.rs`, `docker/Dockerfile.*` or the scanner-image docs, and always before a release (`just tag`):
   1. Run `just image-pins` (needs Docker). Every line must say `ok`; a `DRIFT` line means the tag now points at a newer digest.
   2. For each drifted image, replace only the digest and keep the tag as it is (`python:X.Y-slim-bookworm`, `node:<major>-bookworm-slim`, and the default `node:26.3-bookworm-slim`). Check that the new image has both `linux/amd64` and `linux/arm64` (`docker buildx imagetools inspect <tag>`).
   3. Update every place the same pin appears: the table in `src/runtime_image.rs`, the `ARG PYTHON_BASE` / `ARG NODE_BASE` defaults in `docker/Dockerfile.python` and `docker/Dockerfile.npm`, and the abbreviated digests in the README "Scanner image configuration" table and `docs/DOCKER_SECURITY.md`.
   4. When a new Python minor or Node LTS major is released, add a row to the table (and the supported lists in the README and docs). Drop an end-of-life version only on purpose: a project that still asks for it falls back to the default with a warning, so note it in the README and `docs/ROADMAP.md`.
   5. The base image changed, so verify for real: `just lint-dockerfiles` (this runs hadolint v2.12.0, the version CI uses; a newer local hadolint missed a `DL3006` that CI reported), `just lint`, `just test`, and one end-to-end scan per manager (`just test-uv`, `just test-npm`). `just test-uv` rewrites `tests/uv/pyproject.toml` and `tests/uv/uv.lock`; restore them with `git checkout -- tests/uv`.
10. Load `understand-code` skill for end-of-session teaching and verification.
