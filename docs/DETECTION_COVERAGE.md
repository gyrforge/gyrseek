**What gyrseek catches, stated plainly**

gyrseek reliably catches supply chain attacks where the malicious behaviour fires *during* `npm install` or `pip install` — specifically the `preinstall`/`postinstall` hook variants and `.pth` file artifacts used in the Shai-Hulud, Axios, CanisterWorm, LiteLLM, Namastex/CanisterSprawl, SAP CAP, Bitwarden, TanStack/Mini-Shai-Hulud, and easy-day-js (Mastra) waves. The Telnyx and `mistralai` (Mini-Shai-Hulud T32) PyPI import-time waves are caught by the import-time scan (see below). The behaviour that triggers a block is any new difference from the baselines in one of five checks (each also runs at import time, with its own allowlist), or a failed or timed-out install or load:

- **New network connection** to GitHub Releases (`github.com/oven-sh/bun/releases/...`) — the Bun download
- **Process execution** — *any* newly introduced program execution (not just bun/deno). Previously only a `bun`/`deno` allowlist was captured; now every `execve` is recorded and diffed, so a variant using `node`, `python`, `deno`, `curl`, `wget`, or any other runtime as the payload runner is equally caught.
- **Git clone** — a newly introduced install-time `git clone`, including risky options such as `-c`/`--config`, `--upload-pack` or `--template`.
- **Sensitive file read** — a newly introduced successful read of a credential or configuration file (`~/.aws/credentials`, `~/.npmrc`, `.env`, and similar).
- **Post-install file artifact** — `.pth` files with executable content, unexpected runtime binaries, native binaries, large files, or files dropped outside the install tree that are not present in baselines (see [Post-Install Artifact Detection](DETECTION.md#post-install-artifact-behavior-detection)).
- **A package whose install fails** (`install_failed`) or whose load times out or newly fails (`import_failed`) is blocked too.

Any one of these is enough to block the install before it is forwarded. The artifact inventory and the import-time scan run only in the Docker sandbox: `--no-sandbox` (host mode) does neither, and has no isolation.

Separately from the behavioural checks, gyrseek refuses registry and index redirects, verifies lockfile hashes against the public registry, and installs lockfiles frozen. Those close "install something other than what was scanned" routes rather than detect an attack wave, so they are not in the table.

**The core gap — deferred Python execution**

Several PyPI waves (including Shai-Hulud: Hades/Miasma, Shai-Hulud: Bioinformatics/MCP, TeamPCP LiteLLM, TeamPCP Telnyx, and TeamPCP `mistralai`/Mini-Shai-Hulud T32) use `.pth` files and import hooks specifically to survive install-time scanners. Telnyx (T26) avoided postinstall hooks entirely, placing `FetchAudio()` and `setup()` calls at module scope in `_client.py` — the payload only fires on `import telnyx`, not during `pip install`. `mistralai`/Mini-Shai-Hulud (T32) used the same pattern: a cleartext backdoor appended to `mistralai`'s `__init__.py` at module scope. The sequence:

1. `pip install evil-pkg` runs inside gyrseek's sandbox — the `.pth` file is written to `site-packages`. The **post-install artifact scan** catches it (detects `.pth` files with executable imports) before the container exits, and blocks the host command. Install-time process execution and network may show nothing anomalous, but the artifact diff fails closed.
2. The next time *any* Python interpreter starts on the host, `.pth` fires, downloads Bun from GitHub, and runs the stealer — but the package was already blocked at step 1.

The install window ends when `pip install` exits; the import-time scan described below extends the observed window to loading the package.

**What closes this gap now**

The **post-install file inventory** (implemented, see [dedicated section](DETECTION.md#post-install-artifact-behavior-detection)) runs inside the Docker container after each install probe, recording every installed file via `find /work -type f` and classifying findings on the Rust side (`.pth` with executable content, binary executables, unexpected runtime binaries, files >10 MB) before the container exits. Findings are diffed across versions: a `.pth` file newly introduced in the current version (not seen in baselines) fails closed. This catches the Hades/Miasma `.pth` write-to-disk gap — the `.pth` file is written during install and detected inside the same container session.

The remaining gap for `.pth`-based attacks is T1b (deferred bun download-and-execute on next interpreter startup). Even though the `.pth` file is now caught at T1, a container escape or interpreter-startup interception would be needed to catch the execution phase. A post-install interpreter trigger step (start Python with the installed packages on `sys.path` to force `.pth` execution) remains on the roadmap for future hardening.

**Import-time scan.** The Telnyx import-time pattern (T26) and `mistralai` (T32) put malicious code at module scope in a legitimate source file, so there is no artifact to flag and the install trace is clean. After each install probe the sandbox therefore **loads the installed package** under the same strace, as the same unprivileged user, and diffs that second trace against the baselines' loads (a load is compared with a load, an install with an install). The modules loaded are those of the package and of every dependency the install added, taken from the files the installation recorded, so a distribution whose import name differs (`pyyaml` / `yaml`) works, and under a namespace directory (`acme/widgets/__init__.py`) the real package is loaded, not the empty namespace. For Node every package in `node_modules` is loaded through the entry its `package.json` gives it, decided before anything is evaluated: `import()` when the root of `exports` (or `main`) has an `import` entry, `require()` when it has only a `require` entry. An error inside an `import` entry, also one raised by something it imports, is a failure and is never rescued by the `require` entry (the one exception is a native `.node` addon as the package's own entry); a package with no root entry (subpath exports only, a platform binary) has nothing to load; a package with no entry point (a command-line tool with only a `bin`) has nothing to load.

- Findings are reported "at import time" and blocked under their own reasons (`import_process_exec_anomaly`, `import_network_anomaly`, `import_sensitive_file_read_anomaly`, `import_git_clone_anomaly`, `Suspicious artifact(s) discovered at import time`). Files the load created are inventoried and compared with the baselines' loads.
- Each kind of finding has its own allowlist for this phase: `import_ip_allowlist`, `import_domain_allowlist`, `import_git_clone_allowlist`, `import_process_exec_allowlist`, `import_artifact_allowlist` and `import_sensitive_file_access_allowlist`. **An install-time allowlist entry never allows anything at import time, and the reverse holds too.**
- A load that **times out** (`import_timeout_seconds`, default 300, `0` falls back to 300) blocks the package as `import_failed`: its trace is partial. A load that **fails** is not suspicious by itself (a system library the slim image lacks, an optional dependency), so: if the candidate fails while a baseline loaded cleanly it blocks as `import_failed` (and what it did before failing is still compared), unless every module that failed did so on a missing dependency (`ImportError`, `ModuleNotFoundError`, `MODULE_NOT_FOUND`), which only warns, since a release that starts to need an optional extra says little about the package (a name a module lacks, `from dep import removed`, is not a missing dependency and still blocks; a log too big to be read in full never qualifies); if the candidate and every baseline fail to load (with the same or different errors), gyrseek only warns, prints the error, and still compares what ran before each failure; a candidate that loads when no baseline could has nothing to compare against and a warning says so. A package that can only load in a custom image needs `GYRSEEK_PY_SCANNER_IMAGE` / `GYRSEEK_NPM_SCANNER_IMAGE`; `--no-import-scan` or `import_scan: false` turns the step off.
- Not covered: submodules the package does not import itself, payloads gated on conditions, work deferred past the load (OPEN #509), `.pth` execution at interpreter start (T1b), and host mode, which does not load packages. See OPEN #488–#493, #495, #497, #498, #500 and #502–#505 and #507–#509. The new-package exemption skips the anomaly checks only: a load that times out, or fails where a baseline loaded cleanly, still blocks.
